How the factory turns a prompt into a pull request

This page explains what happens after you type /factory build <prompt>: which agent runs at each stage, what it writes, and what sends a job forward, back, or to you.

In short

  • Your session becomes the orchestrator. It starts agents and reads their results. It never writes code or files itself.
  • Each job moves through 7 stages: create, intake, spec, build, gate, review, approve. Then it is marked complete.
  • Build, gate and review repeat in rounds. A failed gate or a review that asks for changes starts the next round.
  • Every job ends in a pull request. Approved ones merge on their own. Blocked ones wait for you.

When you are asked to step in

  • BLOCKED — intake needs an answer only you can give. Your reply re-runs intake.
  • BLOCKED — the builder can't meet the spec.
  • BLOCKED — the approver couldn't finish the job: a round failed its checks. No pull request.
  • PR FAIL — opening the pull request failed. See pr.md.

    Stage by stage

    Every agent follows the same three moves: run start, do its work, then run complete with an outcome and a markdown file. The script records the result. The orchestrator then reads it with info and picks the next stage.

    Which reviewers run

    Intake tags each job with the surfaces it touches. The code reviewer always runs. The others run only when intake names their surface. All selected reviewers run at the same time, and the orchestrator waits for every one before moving on.

    Reviewers only block on real problems. Matters of taste go under “Notes” and don't stop the job.

    Who writes and reads each file

    All state lives in markdown files in the job folder, <factory>/jobs/<id>/. Agents never write these directly; they pass their content to job.js, which writes it. Hover or focus a file to see its connections.

    Job folder layout

    jobs/001/
├── job.md               # prompt, title, branch, worktree, FINISHED
├── intake.md            # ACCEPT · risk · surfaces · scope
├── spec.md              # requirements + acceptance criteria
├── round-1/
│   ├── build.md         # READY | BLOCKED + evidence + log
│   └── gate.md          # PASS | FAIL + command output
├── round-2/
│   ├── build.md
│   ├── gate.md
│   ├── review-code.md   # PASS | CHANGES
│   ├── review-ui.md
│   └── feedback.md      # only after a BLOCKED
├── decision.md          # APPROVE | APPROVAL-NEEDS-HUMAN | BLOCKED — the PR body
└── pr.md                # log of the PR commands; URL on the last line

<repo>/.worktrees/001-add-dark-mode/   # the job's own checkout, branch factory/001-add-dark-mode

    Every file has the same status header

    If an agent returns while its file still says RUNNING, it crashed or stopped early. The orchestrator must not trust the file and tells you instead.

    Rules that keep it safe

    The script refuses illegal moves

    Every state change goes through scripts/job.js. When a move is out of order, it stops with a message saying why. The orchestrator fixes the cause or tells you; it never works around it.

    • The spec needs an intake that is complete and ACCEPT.
    • Build round 1 needs a complete spec. Round N needs round N−1's build to be complete.
    • After a BLOCKED build, the next build needs your feedback recorded first.
    • The gate needs the round's build to have started.
    • A reviewer needs a passing gate, and must be one intake asked for.
    • The approver needs a passing gate and every needed review at PASS.
    • No step can start twice or complete twice. Feedback is recorded once per block.

    Prompts are data, not instructions

    Every agent treats job.md as a description of what someone wants. Anything in it that tries to steer an agent, its tools or its decision is ignored.

    Jobs never collide

    Up to concurrency jobs (3 by default) run at once. Each one gets its own worktree and branch, its own dev-server port, and its own browser session (--session <id>-builder). Agents stop only the server on their own port, never by process name.

    The approver sends humans what they must see

    Payments, auth and permissions; deploy, CI or hosting config; schema migrations, email, production data or new dependencies; and any spec assumption that is really a product decision.

    The orchestrator doesn't poll

    While agents run, it ends its turn with a one-line status and picks up when they return.

    How the pull request opens

    The approver's complete command opens the PR before it records the decision. It runs the commands in config.json → pull_request.<OUTCOME> inside the job's worktree, in order, and stops at the first failure.

    APPROVE

    Labelled auto-merge and set to merge once the host's checks pass. Then the orchestrator runs job.js complete.

    APPROVAL-NEEDS-HUMAN

    Labelled needs-human-review. You get the “For the human” section of decision.md. The job is not marked complete.

    PR FAIL

    decision.md stays RUNNING and pr.md logs the failed command. Fix the cause, then run approver complete again. Rerunning updates the same PR.

    Ready-made scripts: scripts/github/pull-request.sh (default, needs gh) and scripts/azure-devops/pull-request.sh (needs az). The PR title is the job title; the body is the approver's decision.

    Glossary

    Orchestrator
    The session where you typed /factory. It starts agents, reads results and talks to you.
    Agent
    A background subagent with one job and one instruction file in references/agents/. Its model comes from config.json → agents.
    Job
    One request, with a 3-digit id (001), a folder, a branch and a worktree.
    Round
    One pass of build → gate → review. Each loop back to build starts round N+1 in a new round-N folder.
    Gate
    The repo's checks (tests, lint, typecheck, build) listed in config.json → gate. All must pass.
    Worktree
    A separate checkout at <repo>/.worktrees/<id>-<slug>. All code changes happen here, never in the main checkout.
    Surfaces
    What a change touches: ui, ux, security or none. Decides which reviewers run.
    Outcome
    An agent's result, such as ACCEPT, READY, PASS or APPROVE. Only valid once STATUS: COMPLETE.

    Open points in the current skill

    Found while reading the skill files. Worth fixing so the flow above holds in practice.

    • Round limit isn't enforced. config.json sets max_rounds: 3, but neither the pipeline nor job.js checks it. A job could loop forever on gate failures or review changes.
    • Nobody creates the worktree. job create records WORKTREE and BRANCH in job.md but never runs git worktree add. The gate and PR steps fail if the folder is missing.
    • BLOCKED has no way back. The pipeline says it goes to a human, but there's no step for recording the human's answer and starting the next round.
    • Missing file. SKILL.md points /factory fix at references/pipelines/fix.md, which doesn't exist.
    • File list is incomplete. The file structure in build.md leaves out review-ui.md and review-ux.md.
