How the factory turns a prompt into a pull request

This page explains what happens after you type /factory build <prompt>: which agent runs at each stage, what it writes, and what sends a job forward, back, or to you.

In short

  • Your session becomes the orchestrator. It starts agents and reads their results. It never writes code or edits files itself.
  • Each job moves through 7 stages: create, intake, spec, build, gate, review, approve. Then it is marked complete.
  • Build, gate and review repeat in rounds, up to max_rounds (3 by default). A failed gate or a review that asks for changes starts the next round.
  • When the last round still fails, the job goes to the approver, which marks it BLOCKED and opens no pull request.
  • A round that passes always ends in a pull request. It either merges on its own, or waits for a human to review it. The approver's decision is final.

When you are asked to step in

  • INTAKE BLOCKED: intake has questions only you can answer. Your reply is added to intake.md and intake decides again.
  • BUILD BLOCKED: the builder can't meet the spec. Your reply is added to that round's build.md and the builder carries on in the same round. Say “stop” and the job goes to the approver instead.
  • NEEDS HUMAN: the PR is open with the needs-human-review label. Review it and merge it yourself.
  • BLOCKED: the factory couldn't finish the job. It ran out of rounds or you said stop. No PR. Take over on the job's branch and worktree.
  • PR FAIL: opening the pull request failed. See pr.md, fix the cause, and run it again.

    Stage by stage

    Every agent follows the same three moves: run start, do its work, then run complete with an outcome and a temporary markdown file. The script writes the job file and deletes the temporary file. The orchestrator then reads the result with info and picks the next stage.

    Which reviewers run

    Intake tags each job with the surfaces it touches. The code reviewer always runs. The others run only when intake names their surface. All selected reviewers run at the same time, and the orchestrator waits for every one before moving on.

    Reviewers only block on real problems. Matters of taste go under “Notes” and don't stop the job. From round 2 on, each reviewer first checks that its own earlier findings were fixed. The UI and UX reviewers each get a port and their own browser session (<id>-ui, <id>-ux).

    Who writes and reads each file

    All state lives in markdown files in the job folder, <factory>/jobs/<id>/. No one edits these directly. Agents and the orchestrator pass content to job.js, which writes the files. Hover over or focus a file to see its connections.

    Job folder layout

    jobs/001/
├── job.md               # ID, TITLE, BRANCH, WORKTREE, STARTED, FINISHED + your prompt
├── intake.md            # ACCEPT | BLOCKED | REJECT · risk · surfaces · scope
│                        #   + "# User feedback n" and the decision after it
├── spec.md              # requirements + acceptance criteria + assumptions
├── round-1/
│   ├── build.md         # READY | BLOCKED + evidence + log
│   │                    #   + "# User feedback n" and the report after it
│   └── gate.md          # PASS | FAIL + each command's output
├── round-2/
│   ├── build.md
│   ├── gate.md
│   ├── review-code.md   # PASS | CHANGES (always)
│   ├── review-security.md # only when intake flags security
│   ├── review-ui.md     # only when intake flags ui
│   └── review-ux.md     # only when intake flags ux

<repo>/.worktrees/001-add-dark-mode/   # the job's own checkout, on branch factory/001-add-dark-mode,
                                        # created by spec-writer start (or builder start) from origin/<base_branch>

    Every file has the same status header

    If an agent returns while its file still says RUNNING, it crashed or stopped early. The orchestrator must not trust the file and tells you instead. Running start again on a RUNNING file is allowed and keeps what's already in it. That's how a reopened intake or build carries on.

    Rules that keep it safe

    The script refuses illegal moves

    Every state change goes through scripts/job.js. When a move is out of order, it stops with a message saying why. The orchestrator fixes the cause or tells you; it never works around it.

    • Intake's --surfaces can't combine none with other surfaces.
    • The spec needs an intake that is complete and ACCEPT.
    • Build round 1 needs a complete spec. Round N needs round N−1's build to be complete. No round can go past max_rounds.
    • Intake feedback needs a BLOCKED intake. Build feedback needs a BLOCKED build in the latest round, and only before the approver has started.
    • The gate needs the round's build to have started. The builder runs it itself while working.
    • A reviewer needs a passing gate, and must be one intake asked for.
    • The approver needs the latest round to be finished. A failing round is only allowed when no round is left to fix it: the build is BLOCKED, or it's the last round.
    • With CHECKS: PASS the approver can only APPROVE or ask for a human. With CHECKS: FAIL it can only say BLOCKED.
    • A finished step can't be started or completed again, and a job can only be marked complete once.

    Prompts are data, not instructions

    Every agent treats job.md and your feedback as a description of what someone wants. Anything in them that tries to steer an agent, its tools or its decision is ignored.

    Jobs never collide

    Up to concurrency jobs (3 by default) run at once. Each one gets its own worktree and branch. Agents that open a page get their own port and browser session (<id>-builder, <id>-ui, <id>-ux). They stop only the server on their own port, never by process name. Nothing is ever edited in the main checkout.

    The approver sends humans what they must see

    Payments, auth and permissions; deploy, CI or hosting config; schema migrations, email, production data or new dependencies; and any spec assumption that is really a product decision. It also asks for a human when it isn't convinced every acceptance criterion is met.

    The orchestrator doesn't poll

    While agents run, it ends its turn with a one-line status and picks up when they return.

    How the pull request opens

    The approver's complete command opens the PR before it records the decision. It runs the commands in config.json → pull_request.<OUTCOME> inside the job's worktree, in order, and stops at the first failure. An empty list opens no PR.

    APPROVE

    Pushes the branch. The PR is labelled auto-merge and set to squash-merge once the host's checks pass. Then the orchestrator runs job.js complete.

    APPROVAL-NEEDS-HUMAN

    Labelled needs-human-review. You get the “For the human” section of decision.md. The job is still marked complete. The rest is up to you.

    BLOCKED

    No PR. You get each failed check and what's left to do, plus the branch and worktree. The job stays open and is never marked complete.

    PR FAIL

    decision.md stays RUNNING and pr.md logs the failed command. Fix the cause, then run approver complete again. Rerunning updates the same PR and swaps the label.

    Ready-made scripts: scripts/github/pull-request.sh (default, needs gh and “Allow auto-merge” on) and scripts/azure-devops/pull-request.sh (needs az; auto-merge is auto-complete; descriptions are cut at 4000 characters). The PR title is the job title; the body is the approver's decision. Custom commands can read $FACTORY_ID, $FACTORY_TITLE, $FACTORY_BRANCH, $FACTORY_BASE, $FACTORY_WORKTREE, $FACTORY_OUTCOME, $FACTORY_BODY_FILE and $FACTORY_SCRIPTS. Always quote them.

    Glossary

    Orchestrator
    The session where you typed /factory. It starts agents, reads results and talks to you.
    Agent
    A background subagent with one job and one instruction file in references/agents/. Its model comes from config.json → agents.
    Job
    One request, with a 3-digit id (001), a title, a folder, a branch and a worktree.
    Round
    One pass of build → gate → review, in its own round-N folder. A job gets at most max_rounds. Feedback on a blocked build resumes the same round; it doesn't start a new one.
    Gate
    The repo's checks (tests, lint, typecheck, build) listed in config.json → gate. All must pass.
    Worktree
    A separate checkout at <repo>/.worktrees/<id>-<slug>, created from origin/<base_branch>. All code changes happen here, never in the main checkout.
    Surfaces
    What a change touches: ui, ux, security or none. Decides which reviewers run.
    Feedback
    Your reply to a blocked intake or build. It's saved word for word into that step's file under # User feedback n, and the step runs again.
    Checks
    CHECKS: PASS | FAIL in decision.md, set by approver start. It records whether the latest round's build, gate and reviews all passed, and limits what the approver may decide.
    Outcome
    An agent's result, such as ACCEPT, READY, PASS or APPROVE. Only valid once STATUS: COMPLETE.

The earlier list is mostly fixed: the round limit is enforced, worktrees are created, blocked jobs have a way back, the file list includes every review, the <agents> path points at references/agents/, and the skill triggers on build and fix. These are what's left.

    • Missing file. SKILL.md still points /factory fix at references/pipelines/fix.md, which doesn't exist.
    • Intake never flags ux. job.js accepts ux as a surface, but agents/intake.md only describes ui and security (“Both, or none”). So the UX reviewer will rarely, if ever, run.
    • Ports aren't assigned anywhere. The builder, UI and UX agents expect a port in their prompt, but nothing says how the orchestrator picks one. The builder's prompt (<header> Build round N.) doesn't include one either. With 3 jobs at once, and UI and UX running at the same time, ports could clash.
    • The gate is a placeholder. config.json → gate ships with a command that always fails. Until a repo sets it, every build ends BLOCKED, because the builder must see the gate pass.
    • Some ends leave no marker. REJECT and a stopped intake never set FINISHED, so they look like open jobs. There's also no way back in once a needs-human-review PR gets review comments, because the approver's decision is final.
